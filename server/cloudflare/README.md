# Cloudflare API — المراحل الأولى والثانية والثالثة

> بعض العبارات أدناه تصف مراحل انتقال سابقة. مسار النشر الحالي للموقع ولوحة الإدارة وملكية كل جزء موضح في [خريطة المعمارية الحالية](../../docs/current-architecture.md). احتفظ بهذا الملف لتفاصيل عقود API والتشغيل المحلي، وتحقق من `client/wrangler*.jsonc` لإعدادات Workers النشطة.

خادم Workers لاستقبال الطلبات وقراءة المحتوى المنشور، ضمن خطة النقل المعتمدة. واجهة الإدارة داخل `client/src/admin/` وخادم .NET الحالي محفوظان؛ هذه المرحلة لا تحول مسارات الإنتاج إلى الخادم الجديد.

## تشغيل محلي

من `server/cloudflare/`، باستخدام Node.js 22 أو أحدث:

```powershell
npm ci --include=optional
npx wrangler d1 migrations apply DB --local
npm run dev
```

ينشئ الترحيل قاعدة محلية داخل `.wrangler/` المستثنى من Git. `wrangler.jsonc` محلي دون حساب أو database ID أو نطاق إنتاج. لا تستعمل `--remote` أثناء الاختبارات. `npm run build` هو dry-run ولا ينشر.

انسخ `.dev.vars.example` إلى `.dev.vars` وأدخل القيم اللازمة محليًا بنفسك أو عبر قناة أسرار آمنة. لا ترسل المفاتيح في المحادثة. لا يقبل النموذج حفظًا إذا غاب DB أو HMAC أو Turnstile أو محدد الطلبات؛ `GET /api/site` يستطيع قراءة قاعدة فارغة ويعيد `{}` كما يتوقع العميل الحالي.

| الإعداد | الاستعمال |
| --- | --- |
| `DB` | D1 binding، لا connection string في الواجهة |
| `BOOKING_HMAC_KEY` | سر لا يقل عن 32 بايت UTF-8 لبصمات IP والرسالة |
| `TURNSTILE_SECRET_KEY` | التحقق الحقيقي من رمز النموذج |
| `TURNSTILE_ALLOWED_HOSTNAMES` | أسماء نطاقات مسموحة، مفصولة بفاصلة، دون بروتوكول أو مسار |
| `PUBLIC_ORIGINS` | أصول إضافية كاملة مسموحة للتطوير، مفصولة بفاصلة؛ أصل API نفسه مسموح دائمًا |
| `BREVO_API_KEY` | سر إرسال البريد |
| `BREVO_SENDER_EMAIL` / `BREVO_SENDER_NAME` | مرسل متحقق منه في Brevo |
| `BREVO_RECIPIENT_EMAIL` | بريد المالك لاستقبال الطلبات |
| `BOOKING_RATE_LIMITER` | binding بحد 9/60، مضبوط في Wrangler |
| `ADMIN_ORIGIN` | أصل نطاق الإدارة كاملًا عبر HTTPS دون مسار |
| `ADMIN_ALLOWED_SUB` | UUID لحساب المالك داخل Supabase Auth؛ لا يكفي تطابق البريد وحده |
| `ADMIN_SESSION_KEY` | مفتاح عشوائي 32 بايت بترميز base64url لتشفير جلسة الإدارة |
| `SUPABASE_PUBLISHABLE_KEY` | مفتاح Auth العام لاستدعاءات الخادم؛ ليس مفتاح Storage السري |
| `ADMIN_CSRF_KEY` | سر لا يقل عن 32 بايت UTF-8 لتوقيع رمز CSRF |
| `ADMIN_RATE_LIMITER` / `ADMIN_REPLY_RATE_LIMITER` | 120/60 لإجراءات الإدارة و6/60 للردود، حسب البريد المتحقق منه |
| `ADMIN_LOGIN_RATE_LIMITER` | 5/60 لكل IP لمحاولات الدخول والاستعادة والتحقق، على Worker الإدارة |

غياب إعداد البريد ينتج `disabled` مع بقاء الطلب محفوظًا. لا تضع الأسرار داخل `VITE_*`. عند الربط السحابي تستخدم `wrangler secret put` أو لوحة أسرار Cloudflare، بعد اختيار الحساب. رقم namespace المحلي `10122026` يُفحص داخل الحساب قبل استخدامه في الإنتاج.

### إعداد دخول الإدارة المنفصل

يبني `client/npm run build` الموقع العام فقط، و`client/npm run build:admin` ملفات اللوحة في `client/dist-admin`. يستخدم Worker الإدارة `client/wrangler.admin.jsonc` مع `run_worker_first: true` لكل الطلبات؛ يبقى نطاق الإدارة الحالي مرتبطًا بـWorker الموقع العام إلى حين اكتمال التحقق والنقل. `.dev.vars.example` مثال أسماء متغيرات فقط، و`ADMIN_ORIGIN` فيه نطاق HTTPS اختباري لأن Cookie الإنتاج لا تعمل عبر HTTP.

قبل تحويل النطاق، أنشئ مستخدمًا واحدًا للوحة داخل **Supabase Auth** (حساب لوحة Supabase نفسه لا يكفي)، وأوقف التسجيل العام، واضبط JWT على 900 ثانية بمفتاح توقيع غير متماثل **ES256**. احفظ UUID المستخدم في `ADMIN_ALLOWED_SUB`، واضبط `SUPABASE_PUBLISHABLE_KEY` و`ADMIN_SESSION_KEY` العشوائي base64url بطول 32 بايت و`ADMIN_CSRF_KEY` العشوائي بما لا يقل عن 32 بايت، عبر Cloudflare Secrets لــWorker الإدارة. لا تُرسل القيم في المحادثة ولا تضعها في Git. أبقِ `SUPABASE_SECRET_KEY` الخاص بالوسائط سرًا على Worker فقط. اجعل قالب Magic Link في Supabase يعرض `{{ .Token }}` حتى يصل رمز دخول من 6 أرقام بعد كلمة المرور. يحتاج الاسترجاع إلى SMTP من Brevo؛ اجعل قالب Reset password يعرض `{{ .Token }}` دون أي رابط، ثم أدخل البريد والرمز في `/recover`. يبقى `/auth/callback` للرسائل السابقة فقط. إن كان عامل TOTP مسجلًا، يظل مطلوبًا في مسار استعادة كلمة المرور؛ فقدانه يتطلب استعادة يدوية من حساب مشروع Supabase.

عمليات `/auth/*` والملفات الإدارية المحمية لا تستعلم D1. مدة الجلسة القصوى 8 ساعات، مع JWT مدته 15 دقيقة وتجديد عند الاستعمال؛ إذا انتهت الجلسة أثناء كتابة فلا يعيد العميل الطلب تلقائيًا. `GET /api/admin/session` وعمليات اللوحة تتطلب إتمام كلمة المرور ورمز البريد، أو جلسة `aal2` سابقة؛ استعادة كلمة المرور لا تمنح الوصول إلى اللوحة. لا تختبر حساب المالك أو رسائله على بيانات إنتاج قبل إعداد معاينة معزولة.

## العقود والسلوك

- `POST /api/booking`: JSON واحد يحوي `name,email,projectDetails,turnstileToken,serviceKey,inquiryCategory`، حد جسم 64 KiB، وقيود الاسم/البريد/التفاصيل 100/255/4000 وحدة UTF-16 بعد trimming بنفس مجموعة whitespace في .NET، بما فيها U+0085 ودون حذف U+FEFF. السبب والباقة null يبقيان متوافقين مع العقد السابق.
- `200`: الطلب محفوظ ومرجع `REQ-...`، مع `notificationStatus`؛ `400`: بيانات أو تحقق أمني مرفوض؛ `409` مع `duplicate_submission`: مطابق سبق إرساله؛ `429` مع `ip_blocked` أو `rate_limited`: حظر/حد عام و`Retry-After`؛ `413/415`: حجم/نوع الجسم؛ `503`: إعداد أو خدمة حفظ غير متاحة.
- `accepted` يعني قبول Brevo، ولا يثبت تسليمًا إلى صندوق الوارد. `failed/disabled/timedOut/unknown` لا تلغي الطلب المحفوظ. لا retry للبريد أو للكتابة غير المؤكدة.
- التطابق حسب الاسم والبريد والسبب والتفاصيل من IP نفسه خلال 30 دقيقة؛ تغيير الباقة وحده لا يجعله طلبًا جديدًا. الإرسال الأصلي ثم أربع إعادات تعطي تكرارًا، والإعادة الخامسة تبدأ حظر IP لكل الرسائل 30 دقيقة دون تمديد إضافي عند المحاولات أثناء الحظر.
- IP يؤخذ من `CF-Connecting-IP` الذي تفرضه Cloudflare عند تشغيل Worker؛ لا تثق بهذا header في خادم Node مكشوف خارج Cloudflare. لا يُحفظ IP أو رمز Turnstile في inquiry، وتزال بصمات الحماية المنتهية بتنظيف محدود كل 6 ساعات.
- مهلة Siteverify 3 ثوانٍ. بعد الحفظ تشترك محاولة البريد وتسجيل نتيجتها في الوقت المتبقي من ميزانية 9 ثوانٍ منذ بدء المعالج، بحد أقصى 5 ثوانٍ للبريد و3 للتسجيل؛ يترك ذلك وقتًا لرد العميل ذي مهلة 10 ثوانٍ. انتهاء الميزانية يرد نجاح الحفظ مع `unknown`، ولا يبدأ بريدًا بعد انتهاء الميزانية. كتابة D1 الجارية لا يمكن إلغاؤها، ولا يعاد إرسال البريد أو تحديث غير مؤكد. تأخر الحفظ الأساسي أو الشبكة ما زال قد يتجاوز مهلة العميل؛ يلزم قياس النسخة المعزولة قبل الإنتاج، ولا يُدّعى ضمان الزمن أو CPU Free.
- `GET /api/site`: منشور `pricing/content/pages` فقط، ETag/304، cache داخل isolate لمدة 30 ثانية مع مشاركة القراءات الجارية. لا cache عالمي فوري، ولا طلب خاص عند تغيير اللغة أو دوران السلايدر.
- `/api/admin/*` متاح محليًا لإدارة الطلبات والأسعار والعروض والمحتوى والصفحات؛ لا يغيّر توجيه الإنتاج. النطاق العام `ahmad-makatreh.vip` و`www` يردان 404 لهذه المسارات، وغياب إعداد الإدارة يرد 503 دون قراءة D1.

## ميزانية قاعدة البيانات المقاسة محليًا

| العملية | جولات D1 | عبارات SQL |
| --- | --- | --- |
| إرسال صحيح بباقة معروفة أو null | batch ذري واحد + تحديث نتيجة واحد إن بقي وقت للتسجيل | 4 + 1 عادةً؛ 4 عند نفاد الميزانية قبل التحديث |
| تكرار أو حظر IP | batch واحد، لا بريد | 4 |
| رفض بيانات/حد عام/Turnstile | 0 | 0 |
| باقة مضافة من الإدارة | قد تضيف قراءة snapshot عند cache miss | SELECT واحد إضافي فقط |
| `/api/site` مع cache بارد | 1 | SELECT واحد محدود |
| `/api/site` دافئ أو OPTIONS | 0 | 0 |
| cron تنظيف | batch واحد | 2، بحد حذف 1000 صف لكل جدول |
| نبضة Supabase كل 3 ساعات | طلب RPC واحد إلى Supabase | 0 |

في fixture الإرسال الأول: 7 صفوف مقروءة و7 مكتوبة؛ الإرسال ثم ست إعادات: 32 مقروءة و20 مكتوبة إجمالًا، وفق D1 metadata. الصفوف والفهارس تؤثر في الفوترة؛ عدد جولات binding أو HTTP ليس عدد الصفوف. هذه قياسات معزولة، لا تقدير عدد مستخدمين أو ضمان استهلاك إنتاج.

## التحقق والاستئناف

```powershell
npm test
npm run build
```

الاختبارات تستخدم D1 محليًا حقيقيًا بلا persistence أو remote bindings، وتمثل ردود الخدمات الخارجية في الاختبارات فقط. اختبار runtime يبني حزمة Worker ويفحص الترحيلات ومحدد 9/60 وcron في workerd. لا يحتوي المنتج bypass للتحقق الأمني أو APIs وهمية.

cron لا يعمل تلقائيًا بمرور الوقت في `wrangler dev`؛ اختُبرت دعوته صراحةً داخل runtime. في الإنتاج، يبقى تنظيف D1 كل 6 ساعات، وتُرسل نبضة RPC إلى Supabase كل 3 ساعات دون قراءة أو كتابة D1. يحتاج RPC إلى إنشاء `supabase/project_heartbeat.sql` مرة واحدة في SQL Editor وإلى سر `SUPABASE_SECRET_KEY` في Worker. النبضات تقلل احتمال إيقاف الخطة المجانية لكنها لا تضمن تجاوز سياسة الخمول لدى Supabase.

حالة كل المراحل والحسابات والنتائج في `docs/cloudflare-integration-progress.md`. لم يُتحقق من وصول بريد فعلي أو CPU/حصة الإنتاج بعد؛ تلك اختبارات النسخة المعزولة عند توفر الحسابات.

### موارد المعاينة — المرحلة5A

المالك اعتمد خطة تجهيز الموارد ثم اختار تأجيل إضافة وسيلة الدفع. أُنشئت D1 فقط في الحساب المعتمد `fe25e25f13db2c636fd743e41c8a47e1`:

| المورد | الحالة |
| --- | --- |
| D1 `ahmad-makatreh-preview` | المعرف `7b1d12c7-8d63-49c2-b9ec-fec22dfc5f3f`، منطقةWEUR؛ أربعة ترحيلات مطبقة وثمانية جداول تطبيق فارغة |
| R2 `ahmad-makatreh-media-preview` | اسم مخطط، لم يُنشأ؛ ينتظر تفعيل R2 بواسطة المالك |
| Worker `ahmad-makatreh-preview` | إعداد محلي جاهز فقط؛ لم يُنشر لأن ربط R2 غير مكتمل |

`wrangler.preview.jsonc` إعداد مستقل عن المحلي والإنتاجي، ويثبت الحساب وUUID، ويعطل workers.dev وVersion URLs والطرق وcron. لا متغيرات سرية أو توجيه إنتاج، ولا DB polling. محددات9/120/6/6 لكل60ثانية لها namespaces مستقلة. جدول هذه الفقرة يسجل نتيجة5A؛ اعتمد المالك لاحقًا استبدال التخزين السحابي بـSupabase في5B، كما في القسم التالي.

الإنشاء استعمل `d1 create ahmad-makatreh-preview --update-config=false`، ثم `d1 migrations list/apply DB --remote --config wrangler.preview.jsonc`. لا تُعد إنشاء القاعدة أو تطبيق الترحيلات المكتملة عند الاستئناف. `data_base_1` والموقع الإنتاجي لم يُستعملا لهذه الخطوة.

استعلام التحقق الأول ذو9فروعUNION رفضه D1 برمز7500؛ استعلامSELECT واحد يعيد أسماء الترحيلات وأعداد الصفوف لكل جدول نجح بـ4صفوف مقروءة وصفر كتابة. CLI الترحيلات ينفذ bookkeeping وعبارات مخطط متعددة؛ لا يُحسب التجهيز كله كعمليةSQL واحدة. لا اختبار تحميل أو بيانات إنتاج. الدليل والاستئناف: `.superpowers/sdd/2026-10-12-cloudflare-phase-5-resources/`، والخطة `docs/superpowers/plans/2026-10-12-cloudflare-phase-5-resources.md`.

التحقق المحلي لهذه الخطوة:127/127اختبارWorker دون تخطي أو فشل، منها4حراس إعدادRED→GREEN؛ بناء إعداد المعاينةdry-run ناجح160.27KiB/gzip39.80KiB. أسماءbindings فيdry-run لا تثبت وجودR2؛ لم يُنشرWorker. إصدار الإنتاج وبصمات.NET المحمية لم تتغير. بقية الخطة والمراجعة المستقلة النهائية تنتظران اكتمالR2 وWorker؛ لا يُدّعى اكتمالمرحلة5A.

## Supabase Storage — المرحلة5B

اعتمد المالك التخزين للملفات فقط، مع إبقاء Workers/D1 وعقود الإدارة وR2 المحلي. اختيار `MEDIA_PROVIDER=supabase` يتطلب `SUPABASE_URL` و`SUPABASE_STORAGE_BUCKET` وسر الخادم الحديث `SUPABASE_SECRET_KEY`؛ الإعداد الناقص يفشل مغلقًا دون الرجوع إلى R2. لا قيمة سرية في المثال أو Git أو العميل؛ ضع السر عبر إدارة أسرار Cloudflare. إعداد المعاينة يثبت المشروع `kghmejpjvbmcivnlnkgf` والحاوية `ahmad-makatreh-media-preview`، دون ربط R2 أو تغيير D1 وترحيلاتها.

الحاوية الخاصة يجب أن تمنع Public، وتحدد10485760بايت والأنواع PNG/JPEG/WebP/PDF. الروابط canonical في استجابة الإدارة لا تُعرض علنًا ما دامت الحاوية خاصة. لا links موقعة داخل المحتوى، ولا endpoint لتجاوز Access. إتاحة وسائط التشغيل العامة والنطاقات وAccess والبريد والمتصفح تحتاج مرحلة الربط اللاحقة.

الرفع العادي: عمليتاSQL ورفع Storage واحد. المحاولة المطابقة المكتملة: SQL واحد وصفر Storage. المكتبة: SQL واحد وصفر Storage.list. الأرشفة تبقي الملفات لحماية التاريخ، وميزانيتها3–9SQL؛ لا حذف أو scan تخزين عند فتح المكتبة. المهلة45ثانية، تحويلاتHTTP لا تُتبع، ونتيجة رفع/INSERT مجهولة تحفظ الملف للتوفيق دون retry تلقائي. اختبارات workerd تستعمل نقل Storage في الاختبارات فقط؛ ليست إثباتًا لتشغيل الخدمة المستضافة أوCPU المجاني.

### أدوات الملفات الخاصة

`scripts/supabaseMediaTools.js` يوفر `probe` و`backup` و`restore`، دون jobs أو polling. يحتاج عملية Node مضبوطة مؤقتًا بمتغيرات Supabase المذكورة. فحص السياسات يحتاج أيضًا مفتاح `SUPABASE_PUBLISHABLE_KEY` الحديث؛ غيابه يمنع اعتبار الفحص مكتملًا. يدخل المالك السر في ذاكرة العملية عبر prompt مخفي أو إدارة أسرار؛ لا يكتبه في أمر أو ملف بيئة أو محادثة. حدّد المشروع والحاوية في flags؛ اختلافهما عن البيئة يرفض قبل الاتصال.

من مجلد `server/cloudflare/`، هذه أمثلة بلا أسرار. دليل الفحص/النسخ يجب أن يكون **جديدًا** ومخزنه خاصًا خارج Git والموقع العام؛ على Windows راجع أذونات المجلد الموروثة.

```text
node scripts/supabaseMediaTools.js probe --project-ref kghmejpjvbmcivnlnkgf --bucket ahmad-makatreh-media-preview --directory PRIVATE_NEW_PROBE_DIRECTORY
node scripts/supabaseMediaTools.js backup --project-ref kghmejpjvbmcivnlnkgf --bucket ahmad-makatreh-media-preview --directory PRIVATE_NEW_BACKUP_DIRECTORY
node scripts/supabaseMediaTools.js restore --project-ref kghmejpjvbmcivnlnkgf --bucket ahmad-makatreh-media-restore-preview --directory EXISTING_BACKUP_DIRECTORY
node scripts/supabaseMediaTools.js backup --project-ref kghmejpjvbmcivnlnkgf --bucket ahmad-makatreh-media --directory PRIVATE_NEW_PRODUCTION_BACKUP_DIRECTORY --public-read
```

غيّر متغير الحاوية إلى الوجهة عند `restore`. الوجهة يجب أن تكون مختلفة، فارغة وخاصة بالحدود نفسها. النسخ من حاوية الإنتاج العامة يتطلب `--public-read` الصريح؛ لا يقبله `probe` أو `restore`. الأداة تتحقق من جميع ملفاتmanifest قبل أي رفع، وتقرأ الوجهة نفسها للتحقق من البايتات وmetadata. لا upsert أو prune أو حذف جزئي أو إعادة محاولة تلقائية. ملف evidence يسجل مفاتيح العمليات قبل الكتابة؛ فشل أو انقطاع يحتفظ به، وتكرار نفس العملية لا ينشئ ملفات أخرى. لا تُعد تشغيل العملية بعد نتيجة مجهولة للحصول على تقرير نجاح؛ افحص المفاتيح المعروفة أولًا.

فحص `probe` يتحقق أولًا من مفتاحpublishable بطلب GET محدود لقائمة bucket باسم الهدف وlimit1؛200وقائمة صالحة دليل قبول المفتاح في المشروع. خطأ401 للمفتاح لا يثبت سلامة السياسات. ثم يرفع5ملفات اصطناعية، منها10MiB، وينزلها للتحقق من البصمات والأنواع، ويختبر رفض الرابط العام والقراءة والرفع بمفتاحpublishable. يفك ردStorage المحدود: AccessDenied/403، أوNoSuchBucket/NoSuchKey/404 للقراءة؛ تقبل صيغةHTTP400 الرسمية معstatusCode الداخلي الصحيح. خطأquota أو503 أوJWT أو400عام لا يعد نجاحًا.15HTTP فيfixture الفحص؛ ليس فحصًا دوريًا أو طلبًا إضافيًا لكل رفع. هذا الفحص لا يثبت منعUPDATE/DELETE أو سلامة السياسات العامة الأخرى؛ راجع سياساتbucket داخل حساب المالك. لا ينظف الملفات تلقائيًا. النسخ يقرأ كل الملفات، بما فيها المؤرشفة والأيتام المحتفظ بها، في صفحات100 متتابعة مع كشف تكرار الصفحات/المجلدات.

manifest بصيغة `ahmad-site-supabase-media`/version1 يحفظ مفاتيح الملفات وأسماء أقراص آمنة وبصماتSHA-256 وأنواعها وCache-Control وmetadata المتاحة؛ ليس نسخةSQL. أوقف عمليات الإدارة أثناء snapshot، وانتظر العمليات الجارية، ثم خذ SQL لـD1 أيضًا وفق إجراء المرحلة الرابعة. النسخ من قاعدة Supabase لا يتضمن بايتاتStorage. تبقى ملاحظة دقة تصدير D1 المحلي وحاجته إلى helper قاعدة مغلقة كما هي؛ تصدير D1 السحابي يحتاج تحققًا مستقلًا.

الاختبار المحلي استعاد8جداول فعلية و103ملفات إلى وجهة مستقلة، مع العربية والتاريخ وInt64 `9007199254740993`. عناوين المصدر محفوظة فيSQL؛ نشر استعادة إلى حاوية/مشروع مختلف يحتاج تحويل عناوين مراجع المحتوى والتاريخ وmetadata بصورة مراجعة، ولا تنفذه هذه الأداة. قائمةStorage الفعلية لا تتضمنcustom metadata؛ النسخ والتحقق يطلبان تفاصيل كل ملف عبرGET `/object/info/{bucket}/{key}` المحدود، ويقرآن حقل`metadata` منه. هذه طلبات ضرورية لحفظ البيانات، في إجراء النسخ الصريح فقط؛ المكتبة والرفع المعتاد لا يطلبانها. فيfixture ذي103ملفات ومجلد: النسخ210HTTP (bucket واحد،3قوائم،103تفاصيل،103تنزيلات)، والاستعادة314HTTP؛ لا استعلامD1 من أدوات الملفات، ولا يُدعى صفرSQL داخلي في مزودStorage. حركة الملفات لها حصةSupabase منفصلة عنD1. الحساب والحاويات والمفاتيح والاستعادة المستضافة غير متحقق منها حتى اكتمال خطوات المالك.

## إدارة الطلبات — المرحلة الثانية

يتحقق كل إجراء من جلسة مشفرة في cookie خاصة بالمضيف `__Host-AdminSession`، ثم من JWT صادر عن Supabase Auth بتوقيع ES256 وissuer/audience/expiry و`sub` مطابق لـ`ADMIN_ALLOWED_SUB`، مع إثبات رمز البريد المرتبط بجلسة كلمة المرور أو مستوى `aal2` لجلسة سابقة. لا يُقبل Bearer أو ترويسة Access بديلة. تُشارك قراءة JWKS الجارية وتُخزّن المفاتيح ساعة، مع cooldown دقيقة ومهلة 5 ثوانٍ؛ لا قراءة مفاتيح لكل إجراء. جلسة `GET /api/admin/session` تصدر cookie CSRF خاصة بالمضيف `__Host-AdminAntiforgery` مع HttpOnly/SameSite=Strict/Secure. الكتابة تتطلب Origin مطابقًا و`X-Admin-CSRF` مطابقًا للـcookie وتوقيعًا مرتبطًا بالـ`sub`. لا جلسات داخل D1، وكل ردود الإدارة `no-store`.

الصفحات والفلترة وتغيير الحالة والملاحظات تحافظ على عقود العميل الحالي. cursor هو ticks لـ.NET مع GUID، بدقة 100ns، وليس Base64. ترحيل `0002` يضيف الردود والفهارس ويحافظ على لحظات التواريخ السابقة. الحفظ المشروط يمنع نجاح تعديلين من النسخة نفسها، حتى ضمن ميلي ثانية واحدة. نسخة JSON بتنسيق `ahmad-site-inquiries` وإصدار 1 تحتفظ بالحالة الرقمية 0–4؛ حالات القائمة والتفاصيل تبقى أسماء. الاستيراد يضيف المفقود فقط حسب المعرف أو المرجع، ويحافظ على النصوص العربية والملاحظات والتواريخ، ولا يرسل بريدًا أو يعيد بيانات الحماية المؤقتة.

الرد اليدوي يحتفظ بمعرف العملية والرسالة قبل إرسال بريد plaintext. `accepted` قبول Brevo، وليس إثبات وصول؛ `failed` رفض، و`unknown` نتيجة غير مؤكدة، و`pending` عملية محفوظة لم تُؤكد نتيجتها. مهلة الإرسال 12 ثانية وتسجيل النتيجة 5 ثوانٍ؛ لا retry تلقائي لأي منهما. عملية الإرسال وتسجيل النتيجة الواحدة مسجلة في `ctx.waitUntil` لحماية استمرارها عند انقطاع المتصفح، مع انتظار العملية نفسها للرد الطبيعي ([مرجع Cloudflare](https://developers.cloudflare.com/workers/runtime-apis/context/)). غياب المرسل يحافظ على استجابة 503 القديمة بعنوان `SMTP replies are not configured.` للتوافق مع العميل. retry بالمعرف نفسه يقرأ العملية حتى عند غياب إعداد البريد. حد JSON للإدارة 2 MiB، باستثناء استيراد الطلبات بحد 10 MiB كي يستوعب 100 سجل بأقصى أطوال الحقول وترميز JSON؛ والقيود النصية بوحدات UTF-16 كما في .NET.

في fixture بسجل واحد: القائمة قرأت صفًا، الحالة قرأت صفين وكتبت واحدًا، الملاحظات قرأت واحدًا وكتبت واحدًا، التصدير قرأ واحدًا، وإعادة الاستيراد قرأت واحدًا دون كتابة. `D1.first()` يخفي metadata؛ لذلك عدد صفوف قراءة التفاصيل/العملية غير مقاس بهذا الوسيط، ولا يُعتبر صفرًا. ميزانية SQL أعلاه مستقلة عن عدد الصفوف والفوترة.

المراحل الثلاث محلية؛ الوسائط في الرابعة. ربط Supabase Auth بهوية المالك وتوثيق بريد الاستعادة واختبار المتصفح وقياس CPU/logout بوابات المرحلة الخامسة، قبل اعتماد النشر.

التحقق النهائي للمرحلة الثانية: 68/68 اختبار خادم، 14/14 اختبار إدارة في العميل، بناء العميل وWorker dry-run ناجحان؛ lint الخادم بلا تحذيرات، والعميل مع تسعة تحذيرات سابقة محفوظة. اختُبرت مفاتيح RSA مختلفة، cooldown ثم refresh مشترك، مهلة JWKS فعلية نحو 5 ثوانٍ، وعشرون تحققًا باردًا داخل workerd بطلب مفاتيح واحد. عالج customFetch إعادة ضبط JOSE للطلب الجاري في Workers بمشاركة النص المحمّل وإنشاء Response لكل مستدعٍ. اختُبر تسجيل `waitUntil` في workerd والاستكمال مع إشارة abort في Node؛ انقطاع اتصال فعلي على الإنتاج لم يُختبر، وبقي ضمن مرحلة الربط.

## الأسعار والعروض والمحتوى والصفحات — المرحلة الثالثة

تستعمل المحررات الموجودة نفس عقود `GET/PUT /api/admin/documents/{pricing|content|pages}`. كتابة مسودة كاملة تحتاج `expectedRevision`؛ النشر عبر `POST .../publish` واستعادة المنشور السابق بـ`restorePrevious:true`. `GET .../history?before=` يعيد 25 ملخصًا وصفًا إضافيًا للترقيم، و`POST .../restore` يحفظ النسخة المختارة في المسودة فقط. `GET /api/admin/backup/documents` يصدر المسودة والمنشور للمستندات الثلاثة، دون التاريخ أو الوسائط أو الطلبات.

الترحيل `0003` إضافي يحافظ على المنشور وأجزائه القديمة، ويجعل مسودته النسخة1؛ لا يخترع توقيتًا أو تاريخ نسخ قديمًا. الأجسام ثابتة، بأجزاء BLOB حتى512KiB وعشرة أجزاء لكل جسم. الحفظ المشروط والأجزاء وسجل النسخة في batch ذري واحد؛ التكرار أو التعارض لا يترك أجزاء يتيمة. النشر والاستعادة يعيدان استخدام الأجسام. تحفظ أرقام Int64 في JSON كأرقام دقيقة داخل الخادم؛ العميل الحالي يستخدم JavaScript Number، لذا لا يُدّعى تحرير أرقام تتجاوز دقته من المتصفح.

لا autosave أو polling. الكتابة وترتيب الأقسام والمعاينة وفتح ملف النسخ تحدث محليًا؛ الحفظ والنشر والاستعادة إجراءات صريحة. cache العميل الحالي60ثانية، والتاريخ يُفتح عند الطلب؛ النشر يبطل cache المحلي للعرض العام فقط. القراءة السابقة الجارية لا تستحوذ على قراءة جديدة بعد النشر. ## الوسائط والاستعادة — المرحلة الرابعة

الترحيل الإضافي `0004_media_assets.sql` يحفظ metadata للوسائط دون تغيير بيانات الطلبات والمستندات. إعدادا التشغيل هما binding باسم `MEDIA` ونطاق HTTPS عام في `MEDIA_PUBLIC_BASE_URL`. تبقى إعدادات هذا المشروع محلية؛ يلزم تفعيل R2 واختيار bucket والنطاق أثناء مرحلة الحسابات. محتوى R2 هنا عام، ولا يستقبل نسخ الطلبات أو أسرار التشغيل.

المسارات `/api/admin/media` و`/media/{uploadId}` و`/media/{id}/archive` تعمل تحت جلسة الإدارة الموثقة؛ الكتابة تتطلب Origin وCSRF. الرفع binary بطلب واحد، مع UUID ثابت عند إعادة المحاولة، وحد 10 MiB وفحص توقيع PNG/JPEG/WebP/PDF. يحدد الخادم النوع والامتداد؛ الفحص ليس فكًا كاملًا للصور أو مسحًا للبرمجيات الضارة. محدد الرفع 6/60 ثانية لكل هوية مصرح لها، إضافة إلى حد الإدارة العام؛ لا SQL لهذا المحدد.

المفتاح عشوائي مع شرط إنشاء فقط، وSHA-256، وCache-Control سنة/immutable؛ PDF مرفق والصور inline. تُحفظ metadata بعد تأكيد PUT فقط. مهلة التخزين45ثانية لا تلغي PUT الجاري؛ يبقى الملف الذي يصل متأخرًا دون سجل نجاح. إذا كان حفظ metadata غير مؤكد، يبقى الملف ويستطيع تكرار الهوية العثور على السجل إن حُفظ. حذف ملف المحاولة الخاسرة يحدث فقط عند تأكيد أن INSERT لم يملك السجل. لا retry تلقائي ولا حذف للملفات غير المحسومة.

### نسخ كاملة واستعادة

نسخة `/api/admin/backup/documents` ونسخة الطلبات الحالية تظلان بصيغتيهما؛ ليستا نسخة كاملة لملفات R2 أو تاريخ كل المستندات. النسخة الكاملة إجراء تشغيلي صريح، دون endpoint يعيد كل البيانات أو فحص خلفي دوري.

1. اختر موارد المصدر بالاسم والمعرف، وأوقف عمليات رفع/أرشفة الوسائط من الإدارة أثناء أخذ النسخة وانتظر العمليات الجارية. احفظ النسخة في مخزن خاص خارج Git وbucket العام.
2. صدّر SQL كاملاً لـD1 المختار. أمر Wrangler المتحقق منه: `wrangler d1 export DB --remote --output <private-backup.sql> --config <approved-config>`. هذا مثال للمرحلة الخامسة؛ لم يُنفذ على حساب المالك.
3. انسخ جميع ملفات R2، بما فيها المؤرشفة والملفات المحتفظ بها من عمليات غير محسومة، دون prune أو `sync` يحذف بيانات. يمكن استعمال `rclone copy` للنسخ؛ نسخ البايتات وحده لا يكفي: يلزم manifest خاص يحفظ المفاتيح والأحجام وSHA-256 وHTTP/custom metadata والتحقق من حفظها عند الاستعادة.
