# تصميم دخول الإدارة وحماية ملفاتها

التاريخ: 2026-10-14
الحالة: للمراجعة قبل خطة التنفيذ

## الهدف

تعمل اللوحة على `admin.ahmad-makatreh.vip` داخل المشروع الحالي. قبل الدخول لا يستطيع الزائر تنزيل واجهة الإدارة أو استدعاء بياناتها وعملياتها؛ يرى صفحة دخول واستعادة حساب صغيرة فقط. بعد الدخول بكلمة المرور ورمز التحقق يستطيع استعمال جميع ميزات اللوحة الحالية. يبقى الموقع العام سريعًا، ولا تُضاف استعلامات D1 لمجرد عرض ملفات الإدارة.

وجود نطاق فرعي يصعّب مصادفة العنوان لكنه ليس إذنًا بالدخول. لا يحتوي المتصفح أو الملفات المنشورة على أسرار الخادم. لا يعتمد التصميم على Cloudflare Zero Trust أو وسيلة دفع.

## الوضع الحالي الذي فُحص

- `client/src/main.jsx` يختار الموقع أو `client/src/admin/AdminApp.jsx` حسب اسم المضيف، لكن Vite يضع الحزمتين في `client/dist` نفسه.
- `client/wrangler.jsonc` يطلب تشغيل Worker قبل `/api/*` فقط؛ بقية الملفات الثابتة تُقدَّم قبل تنفيذ `client/worker.js`. لذلك لا يمنع فحص المضيف الحالي تنزيل ملفات الإدارة من الحزمة العامة.
- `server/cloudflare/src/adminAccess.js` يتحقق من Cloudflare Access وCSRF، و`client/src/admin/AdminApp.jsx` يستعمل رابط الخروج الخاص بـAccess. هذا المسار لا يوفر دخولًا مستقلاً ما دام Access غير مستخدم.
- `/api/admin/*` محصور بالمضيف الإداري في `client/worker.js` وداخل وحدة التحقق. لا يُزال هذا القيد أثناء النقل.

## البدائل والاختيار

| البديل | النتيجة |
|---|---|
| إخفاء الواجهة في React وحماية API فقط | يبقي ملفات الإدارة قابلة للتنزيل، فيخالف أولوية المالك. |
| Worker واحد يفحص كل الملفات أولًا | يمكنه حماية الملفات بعد فصل البناء، لكنه يُشغَّل أيضًا لكل ملف عام، ما يزيد طلبات Worker ويعرض الموقع العام لحدوده المجانية. |
| بناءان وWorker للإدارة، داخل المستودع نفسه | المختار: يحصر فحص الملفات في النطاق الإداري ويحافظ على تقديم ملفات الموقع العام بالطريقة الحالية. |

لا يعني البناء المنفصل قاعدة بيانات جديدة أو نقل `client/src/admin/`. تبقى وحدات API والبيانات القائمة مشتركة في المصدر، ويُعاد استخدام منطقها دون نسخ وظائف الإدارة أو تغيير عقودها.

## حدود الملفات والمسارات

1. يبني النشر العام الموقع وحده؛ لا تصل أي حزمة JavaScript أو خريطة مصدر أو ملف خاص باللوحة إلى أصوله. يبقى `/api/site` و`/api/booking` كما هما.
2. يبني النشر الإداري صفحة الدخول وملفات اللوحة في مخرجات منفصلة. يبدأ Worker الإداري قبل تقديم **كل** طلب لملف أو مسار على نطاق الإدارة.
3. يسمح دون جلسة بملفات صفحة الدخول واستعادة كلمة المرور اللازمة لهما فقط. لا تستورد هذه الملفات كود `AdminApp` أو محرراته. تعيد بقية ملفات اللوحة والمسارات العميقة و`/api/admin/*` رفضًا دون تسريب محتوى.
4. بعد المصادقة الكاملة، يسمح Worker بطلب ملفات الإدارة وAPI. لا يكفي وجود Cookie أو عنوان بريد في الطلب؛ يتحقق من التوقيع والهوية والصلاحية ودرجة المصادقة عند كل طلب محمي.
5. لا يقدّم النطاق العام API الإدارة أو ملفاتها. لا يؤدي طلب `/work/crisis-fund` على نطاق الإدارة إلى عرض الموقع العام؛ بعد الدخول يوجَّه إلى اللوحة أو يرد بمسار إداري واضح.
6. تُرسل ملفات وصفحات الإدارة المحمية بسياسة تمنع التخزين المؤقت العام، وتُختبر العودة للخلف بعد الخروج. تبقى صفحة الدخول متاحة، لكنها لا تحتوي بيانات أو كود إدارة محميًا.

## الدخول والجلسة

- يستخدم حساب مستخدم داخل **Supabase Auth** للمشروع الحالي؛ حساب دخول لوحة Supabase نفسه لا ينشئ مستخدمًا للتطبيق تلقائيًا. ينشئ المالك مستخدم الإدارة، ويوقف التسجيل العام، ثم يربط الخادم صلاحية الإدارة بمعرّف المستخدم الثابت `sub`، لا بعنوان البريد وحده.
- كلمة المرور تمنح مرحلة أولى (`aal1`). إعداد عامل TOTP الأول وإدخال رمزه مسموحان في هذه المرحلة؛ ملفات اللوحة وAPI لا تفتحان إلا بعد `aal2`. بعد الإعداد الأول، لا تسمح إدارة عوامل TOTP الإضافية إلا بجلسة بلغت `aal2`.
- يمر الدخول وتحديث الجلسة عبر Worker الإداري. يحتفظ المتصفح بجلسة محصورة بالمضيف الإداري في Cookie باسم يبدأ بـ`__Host-` ويحمل `Secure; HttpOnly; SameSite=Strict; Path=/` دون `Domain`، ولا تُحفظ رموز الوصول أو التحديث في `localStorage` أو واجهة JavaScript. تحفظ أسرار تشفير/توقيع الجلسة في Cloudflare Secrets فقط.
- يتحقق Worker من JWT بمفاتيح Supabase العامة وخوارزمية و`issuer` و`audience` و`exp` و`sub` و`aal2`. المفاتيح العامة مخزنة مؤقتًا بمدة محدودة؛ لا طلب إلى Supabase ولا استعلام D1 مع كل ملف في الحالة المعتادة.
- تنتهي صلاحية JWT للإدارة بعد 15 دقيقة، ويُفرض حد أقصى للجلسة قدره 8 ساعات من وقت الدخول داخل Cookie المحمي، ولو بقيت جلسة Supabase صالحة. تتولى نقطة تجديد واحدة التحديث عند فتح اللوحة أو الحاجة الفعلية، مع منع تجديدات متزامنة للرمز نفسه. لا إعادة تلقائية لعمليات كتابة قد تكون نُفذت بالفعل. الخروج يبطل رمز التحديث لدى Supabase ويمسح Cookies محليًا؛ قد يبقى JWT صادر سابقًا صالحًا حتى نهاية دقائقه الـ15.
- عمليات الكتابة تحتفظ بالتحقق الموجود من `Origin` وCSRF، إضافة إلى المصادقة. يضاف حد محاولات مستقل للدخول والاستعادة عند Cloudflare قبل استدعاء Supabase، مع رسائل لا تكشف وجود حساب باسم معين.

## أول دخول والاستعادة

1. يدخل المالك بحساب التطبيق الذي أُنشئ له، ويضيف TOTP الأول عبر رمز QR ثم يؤكده. لا تسمح هذه الخطوة بدخول اللوحة قبل نجاح التحقق الثاني.
2. بعد الدخول الكامل، يضيف عامل TOTP احتياطيًا على جهاز مختلف، ويُختبر العاملان قبل التحويل إلى الإنتاج.
3. يستعمل نسيان كلمة المرور رابط Supabase مخصصًا لنطاق الإدارة، مع SMTP من Brevo مضبوطًا لدى Supabase. إعادة تعيين كلمة المرور لا تُعطي `aal2` ولا تلغي TOTP.
4. إذا فُقد العاملان، لا يوجد زر تجاوز عام. يعالج المالك الاستعادة يدويًا من حساب إدارة مشروع Supabase بعد التحقق من هويته؛ لا تملك صفحة الاستعادة العامة صلاحية حذف عوامل MFA.

## الطلبات والتكلفة

| العملية | D1 | الاتصال الخارجي المعتاد |
|---|---:|---|
| عرض صفحة الدخول أو رفض ملف إدارة غير مصرح | 0 | 0 |
| تقديم ملف إدارة بجلسة صالحة ومفتاح عام محفوظ | 0 | 0 |
| تسجيل الدخول أو التحقق من TOTP أو إعادة التعيين | 0 | طلب Supabase Auth بحسب الإجراء |
| تجديد جلسة منتهية | 0 | طلب Supabase Auth عند الحاجة فقط |
| فتح شاشة أو حفظ بيانات إدارية | وفق الاستعلامات الموجودة للشاشة/الإجراء | لا تحقق حي من Auth لكل قراءة عادية |

كل طلب لملف إداري محمي يستدعي Worker الإداري، ولو لم يستدعِ D1. لا تغير هذه الخطة مرور ملفات الموقع العام عبر تقديم الأصول المجاني الحالي. لا polling ولا استعلام جديد لكل render.

## مراحل التنفيذ والتحقق

1. بناء منفصل للموقع واللوحة، مع صفحة دخول صغيرة مستقلة. اختبارات تؤكد غياب حزم الإدارة من مخرجات الموقع العام.
2. Worker إداري يبدأ قبل كل ملف ومسار، ويرفض الملفات المحمية وAPI دون جلسة. اختبارات لمسارات مباشرة، الملفات المعروفة والقديمة، المضيف الخاطئ، وغياب الإعدادات.
3. إدخال Supabase Auth وTOTP والجلسة والخروج مع إبقاء عقود API وميزات اللوحة. اختبارات التوقيع، `sub`، `aal2`، انتهاء الرمز، CSRF، الحدود، وتجديدات الجلسة المتزامنة.
4. استعادة كلمة المرور والعامل الاحتياطي واختبار Brevo SMTP. اختبارات تؤكد أن إعادة كلمة المرور لا تتجاوز TOTP.
5. تجربة محلية ومعاينة معزولة ثم مراجعة إعدادات الحساب والأسرار، وفحص شبكة المتصفح دون جلسة ومعها، قبل نقل `admin.ahmad-makatreh.vip` إلى Worker الإدارة. يُراجع الموقع العام والطلبات والمحتوى بعد النقل، وتُحفظ هوية النشر السابق للرجوع.

لا تُختبر بيانات إنتاج أو يُجرى ضغط على الخدمات الحية. لا يُنشر تغيير في النطاق الحي قبل جاهزية الدخول والاستعادة والتحقق من عدم وصول ملفات الإدارة من المضيف العام. لا يمكن محو نسخة ملفات سبق أن احتفظ بها جهاز خارجي؛ الهدف منع تقديمها مستقبلًا وحماية البيانات دائمًا على الخادم.
