# ملحق التصميم: Supabase Storage للوسائط

التاريخ: 2026-10-13 — الحالة: اعتمد المالك التصور والوثيقة وخطة التنفيذ `../plans/2026-10-13-supabase-storage-phase-5b.md`. وصلة التخزين والتكامل وأدوات النسخ والاستعادة منفذة ومختبرة محليًا؛ إعداد الحساب والمفاتيح والتحقق المستضاف ما زال معلقًا.

## الهدف والقرار المعتمد

تجهيز تخزين الصور والملفات دون إضافة وسيلة دفع حاليًا، مع الحفاظ على ميزات الإدارة الحالية وتقليل طلبات قاعدة البيانات. التوزيع المعتمد: Workers للخادم، D1 للطلبات والأسعار والعروض والمحتوى والصفحات، وSupabase Storage للوسائط فقط. يبدأ التجهيز بحاوية معاينة خاصة، والرفع عبر الخادم المحمي، مع رفع واحد ومنع التكرار.

هذا ملحق لتصميم `2026-10-12-cloudflare-integration-design.md`: يستبدل تجهيز R2 السحابي المقترح بتجهيز Supabase Storage. لا يعيد تنفيذ المراحل الأولى إلى الرابعة، ولا ينقل بيانات التطبيق إلى PostgreSQL أو يغيّر Access وTurnstile وBrevo. يبقى تنفيذ R2 المحلي واختباراته الحالية محفوظين أثناء إضافة مسار التخزين الجديد.

## الحدود والبدائل

الخيار المعتمد يعيد استخدام Workers/D1 المجهزين ويضيف اتصال Storage عبر HTTPS. إبقاء R2 مؤجلًا يستلزم حل شرط وسيلة الدفع، ونقل التطبيق كله إلى Supabase يوسع التغيير ويستبدل تنفيذًا جاهزًا خارج الطلب؛ لا يشمل هذا الملحق أيًا منهما.

حدود المرحلة: وصلة التخزين في خادم Workers، اختبارات العقود والتزامن والفشل وميزانية الطلبات، إعداد حاوية خاصة وربط Worker المعاينة، وإجراءات نسخ الملفات والتحقق من الاستعادة. واجهة React وملفات .NET وقواعدها الحالية لا تحتاج تعديلًا. لا حزم جديدة، أو تعديل لترحيلات D1، أو تشغيل Supabase Auth/Realtime/Edge Functions.

الإنتاج وDNS والنطاق `admin.ahmad-makatreh.vip` وإعداد بريد المالك تبقى ضمن الربط اللاحق. لا تفعيل R2 أو ترقية Supabase أو إضافة بطاقة أو نشر إنتاج ضمن هذا الملحق. اعتماد التصور ليس اعتمادًا لخطة تنفيذ لم تُكتب بعد.

## بنية التخزين والتوافق

تُضاف وصلة صغيرة داخل `server/cloudflare/src/` تستعمل `fetch` الموجود في Workers. تتولى اختيار المزود وإعداد عنوان الملف والرفع وحذف الملف غير المملوك بعد تعارض مؤكد؛ تبقى المصادقة والتحقق والـSQL في مواضعها الحالية.

- إعداد صريح `MEDIA_PROVIDER=supabase` لمسار المعاينة. عند غياب هذا الإعداد يبقى مسار R2 الحالي؛ قيمة غير معروفة أو إعداد Supabase ناقص يفشل مغلقًا دون الرجوع إلى مزود آخر أو إرسال سر إليه.
- إعدادات غير سرية: `SUPABASE_URL` و`SUPABASE_STORAGE_BUCKET`. يثبت إعداد المعاينة عنوان المشروع أعلاه واسم الحاوية، ويزيل ربط R2 غير الموجود من إعداد المعاينة فقط بعد تحديث اختبارات حراسة الإعداد.
- سر الخادم: `SUPABASE_SECRET_KEY`، من نوع `sb_secret_…` الحديث، داخل إدارة أسرار Cloudflare فقط. لا قيم حقيقية في المصدر أو الأمثلة أو المحادثة أو `VITE_*`، ولا تعديل لملفات البيئة الحقيقية أثناء التنفيذ المحلي.
- المفتاح ذو صلاحيات مرتفعة في مشروع Supabase، وليس صلاحية مقصورة تلقائيًا على حاوية واحدة. الخادم يثبت الحاوية ويتحقق من المفاتيح التي ينشئها؛ لا endpoint يتيح استعماله لقراءة مسارات يختارها الزائر. تبقى حماية Access والبريد المسموح وOrigin وCSRF وحد الرفع6/60 قبل أي عملية كتابة.
- يُرسل المفتاح عبر `apikey` إلى أصل HTTPS الخاص بالمشروع فقط. تُرفض عناوين ذات credentials أو query أو fragment أو مسارات إضافية أو أحرف تحكم. لا تُتبع redirects؛ السجلات لا تطبع headers أو السر أو جسم خطأ المزود الخام.
- لا تغيير لعقود `GET /api/admin/media` و`POST /api/admin/media/{id}` و`POST /api/admin/media/{id}/archive` أو حقول `id,url,originalName,contentType,size,createdAtUtc` وحالاتها. تبقى الروابط القديمة والسجل التاريخي كما هما، دون تحويل تلقائي أو إعادة رفع.

## تدفق الرفع والفشل

1. العميل الحالي يرسل طلب binary واحدًا مع UUID ثابت عند إعادة المحاولة. يبقى قفل النقر وحد10MiB، والتحقق الخادمي من UUID والاسم وتوقيع PNG/JPEG/WebP/PDF.
2. يحسب Worker بصمة SHA-256 ويقرأ سجل UUID من D1 مرة. السجل المطابق غير المؤرشف يعاد دون رفع جديد؛ اختلاف البصمة أو الأرشفة يعيد409.
3. الرفع الجديد يستخدم مفتاحًا عشوائيًا جديدًا، وطلب Storage واحدًا وفق عقد HTTP الرسمي، مع `x-upsert:false` ونوع الملف الصحيح وCache-Control الحالي. لا طلب HEAD أو list أو bucket-info قبل كل رفع. تحفظ بصمة الملف أيضًا ضمن metadata الخاصة بالملف لتيسير النسخ والتحقق؛ ليست إثباتًا بأن المزود تحقق بنفسه من البصمة.
4. تؤكد الوصلة نجاح التخزين وفق استجابته الموثقة قبل INSERT في D1. خطأ HTTP أو استجابة غير صالحة أو انتهاء مهلة الرفع لا ينشئ سجل نجاح. يحفظ السجل النوع والاسم والحجم والبصمة والمفتاح والعنوان كما في التنفيذ الحالي.
5. تبقى مهلة الرفع45ثانية ومهلة العميل60ثانية. طلب HTTPS له إلغاء محدود، لكن الإلغاء لا يثبت تراجع التخزين البعيد. لا retry تلقائي لرفع أو كتابة غير مؤكدة؛ تبقى العملية الجارية ضمن عمر Worker المدعوم دون ضمان أنها ستكمل بعد انقطاعه.
6. بعد نجاح التخزين، نتيجة INSERT مجهولة تحتفظ بالملف للتوفيق اللاحق. تعارض INSERT المؤكد يحذف مفتاح المحاولة الخاسرة وحده، ثم يقرأ الفائز؛ الحذف الخارجي محدود بثلاث ثوانٍ، وفشله يحتفظ بالملف ويسجل خطأً آمنًا. لا حذف للفائز أو لكل ملفات UUID، ولا تنظيف خلفي للأيتام.

طلبات الرفع المتزامنة قد تخزن ملفات مؤقتة متعددة قبل حسم UUID في D1؛ المنع الحالي يضمن سجلًا واحدًا وفائزًا واحدًا، وليس عملية Storage واحدة لجميع المحاولات المتزامنة. الاختبار يثبت تنظيف الخاسرين المؤكدين والاحتفاظ بالحالات غير المحسومة.

Supabase يوصي بالرفع القابل للاستئناف للملفات فوق6MB. نبقي الحد والعقد الحاليين10MiB والرفع الواحد، ونتحقق من الحجم الأقصى والانقطاع في النسخة المعزولة؛ لا تُضاف أجزاء TUS أو تُخفض الحدود دون تغيير متفق عليه. تأخر D1 أو الشبكة قد يتجاوز مهلة العميل، فلا يُدّعى ضمان زمن شامل أو ملاءمة CPU Free قبل القياس.

## الحاوية الخاصة وعرض الملفات

حاوية التجهيز خاصة، بحد `10485760` بايت والأنواع الأربعة المحددة. لا سياسات رفع أو حذف عامة، ولا صور أو نسخ طلبات حقيقية أثناء الاختبار. تُقرأ ملفات الاختبار الخاصة عبر طلب خادمي مخول، ويُختبر رفض تنزيلها دون صلاحية. لا روابط موقعة داخل محتوى D1 أو التاريخ؛ انتهاؤها يكسر مراجع الموقع.

العقد الحالي للمكتبة يفترض روابط عامة ثابتة. تحتفظ وصلة Supabase بعنوان canonical من نوع `/storage/v1/object/public/{bucket}/{key}`؛ وجوده في استجابة رفع خاصة لا يجعله قابلًا للعرض العام. لا تُعلن المكتبة جاهزة بصريًا ما دامت الحاوية خاصة. هذا قيد مرحلة التجهيز، ولا يستدعي تغيير الواجهة أو إضافة طلب توقيع لكل صورة.

بعد اختبار الحساب والحماية واعتماد مرحلة الربط، تُجهز حاوية تشغيل منفصلة للمواد العامة، وتُراجع إتاحتها العامة صراحة. التقديم المقترح مباشرة من Storage/CDN، دون مرور كل صورة بخادم التطبيق أو استعلام D1. يبقى الرفع والحذف محصورين بالخادم. PDF يستعمل خيار `download` الرسمي في عنوانه للحفاظ على سلوك التنزيل بدل الاعتماد على دعم Content-Disposition مماثل لـR2. لا وسائط خاصة أو ملفات نسخ احتياطية في الحاوية العامة.

## ميزانية الطلبات

هذه أهداف تحفظ القياسات الحالية لـD1؛ يلزم قياس التنفيذ الجديد. عدد SQL لا يساوي عدد الصفوف المفوترة أو جولات HTTP، وعمليات Supabase أدناه لا تعني صفر SQL داخليًا.

| الإجراء | HTTP من الواجهة | عبارات D1 المستهدفة | اتصال Storage من خادم التطبيق |
| --- | --- | --- | --- |
| اختيار ملف أو تعديل حقول | 0 | 0 | 0 |
| رفع جديد ناجح، دون تعارض | POST واحد | SELECT + INSERT =2 | رفع واحد |
| إعادة محاولة مطابقة لسجل مكتمل | POST واحد صريح | SELECT واحد | 0 |
| تعارض رفع متزامن بعد قراءة أولى فارغة | POST واحد لكل محاولة | حتى3 لكل خاسر: SELECT/INSERT/قراءة الفائز | رفع لكل محاولة بدأت التخزين؛ حذف مفتاح الخاسر المؤكد فقط |
| فتح المكتبة/صفحة cursor عند cache miss | GET واحد | SELECT واحد، LIMIT26 يعرض25 | 0؛ لا قائمة ملفات أو COUNT |
| أرشفة عنصر | POST واحد | 3–9 عادةً لفحص المراجع وrevision؛ المؤرشف سابقًا1، وقد تضيف المنافسة قراءة | 0؛ الملف محفوظ للتاريخ |
| رفض إذن أو CSRF أو حد أو ملف غير صالح | طلب مرفوض | 0 | 0 |
| عرض صورة عامة لاحقًا | تحميل مباشر من Storage/CDN | 0 في التطبيق | طلب تنزيل من المتصفح؛ يؤثر في حصة Supabase |

Supabase يستخدم PostgreSQL لبيانات الحاويات والملفات والسياسات؛ عدد عملياته الداخلية غير مقاس هنا. لا يُضاف عميل PostgreSQL أو استعلام SQL مباشر في مخطط `storage`. تبقى ذاكرة العميل الحالية60ثانية ومشاركة GET الجارية، وتحديث القائمة محليًا بعد الرفع/الأرشفة، دون autosave أو polling أو فحص كل صورة أو تكرار عند كل render.

## النسخ والاستعادة

تتكون النسخة الكاملة من SQL لـD1 ومن الملفات وmanifest خاص خارج Git والتخزين العام. نسخ قاعدة Supabase وحدها لا تتضمن بايتات Storage؛ لا يعتمد هذا التصميم عليها لحماية الوسائط.

- يوقف المشغل رفع/أرشفة الوسائط أثناء النسخ وينتظر العمليات الجارية. قائمة Storage paginated ومحدودة، وتضم الملفات المؤرشفة والمحتفظ بها بعد نتيجة غير مؤكدة؛ لا تُستخرج القائمة من `media_assets` فقط.
- لكل ملف: المفتاح والحجم وSHA-256 وContent-Type وCache-Control وmetadata المتاحة. تُنسخ البايتات إلى مخزن خاص وتطابق بصمتها. لا prune أو overwrite أو SQL مباشر على مخطط Supabase Storage؛ الرفع والحذف عبر API.
- الاستعادة أولًا إلى حاوية وD1 فارغتين ومعزولتين. يُتحقق من جميع الملفات والتاريخ والعربية وأرقام Int64 ومراجع المسودات والمنشورات، ويعاد تنزيل ملف استُعيدت نسخته التاريخية لمقارنة البصمة. استعادة البيانات السحابية تحتاج أدلة فعلية؛ اختبار R2 المحلي السابق لا يثبتها.
- عناوين Supabase مرتبطة بالمشروع والحاوية. إعادة الملفات إلى العنوان الأصلي تحافظ على الروابط؛ حاوية الاستعادة المعزولة لا تتحول تلقائيًا إلى بديل لعناوين المصدر. الاختبار يعاملها مصدرًا مستقلًا حسب المفتاح ويثبت أن بايتات الوجهة نفسها قُرئت.
- النقل إلى مشروع/حاوية تشغيل مختلفة يحتاج جدول تحويل صريح للعناوين، يشمل `media_assets` والمسودات والمنشورات والتاريخ وأجسام المستندات وبصماتها، ولا يستعمل استبدالًا نصيًا خامًا في SQL. إجراء هذا التحويل ومراجعة الروابط شرط في خطة ربط/استعادة التشغيل عند اختلاف العنوان؛ ليس migration تلقائيًا في وصلة التخزين ولا جزءًا من إنشاء حاوية المعاينة.
- فحص تصدير D1 السحابي ودقة Int64 يبقى شرطًا من المرحلة الخامسة. تُحفظ ملاحظة تقريب الأرقام في تصدير Wrangler المحلي؛ لا يُعرض dump غير متحقق منه كنسخة استعادة دقيقة.

النسخ إجراء صريح بطلب المشغل؛ لا يضاف جدول نسخ دوري أو تنزيل متكرر للملفات للمحافظة على نشاط خطة Free.

## التكلفة وحدود التشغيل

بحسب التسعير الرسمي المفحوص2026-10-13: Storage Free له1GB، و5GB نقل غير مخزن مؤقتًا و5GB نقل مخزن مؤقتًا شهريًا، بحصتين مستقلتين. قد تتوقف المشاريع المجانية بعد أسبوع من الخمول. تعرض النسخة حد الاستخدام وأي توقف كفشل خدمة مفهوم؛ لا upgrade تلقائي أو طلبات keep-alive مصطنعة. موارد المعاينة والتشغيل في المشروع نفسه تشترك في الحصة.

البريد عبر Brevo كما في التصميم الأصلي، ولا يتغير عدد رسائل البريد بسبب اختيار Storage. لا تدعي هذه الحدود عدد زوار مضمونًا أو صفر تكلفة مستقبلية؛ يسجل اختبار المعاينة ما قيس بالفعل من طلبات وقراءات/كتابات ووقت CPU وذاكرة ونقل.

## مراحل التنفيذ ومعايير القبول

1. **خطة مكتوبة بعد مراجعة هذا الملحق:** مهام ملفات صغيرة، حراس الإعداد، واختبارات فشل/تزامن/تكلفة محددة. تبقى طريقة التنفيذ المباشر المعتمدة؛ لا إعادة سؤال المالك عن الطريقة.
2. **الوصلة محليًا:** حفظ R2 والتوافق، وعدم تغيير العميل أو .NET أو schema؛ اختبارات HTTP بعينات خدمة خارجية في الاختبارات فقط. تتغطى redirects/تسرب الأسرار/الإعداد الناقص، والأنواع/الحجم، والفشل الجزئي، وUUID والبصمات، وعشرون رفعًا متزامنًا، والمهلات والحذف المحدود والأرشفة وميزانية D1. بناء Worker dry-run ومجموعة الاختبارات المطلوبة ناجحان، ثم مراجعة مستقلة وفق مهارة التنفيذ.
3. **الموارد بعد اعتماد الخطة:** التحقق من المشروع والحاوية والخطة في حساب المالك، وإنشاء حاوية خاصة واحدة عند غيابها، وإدخال السر في Cloudflare بطريقة آمنة. نتيجة إنشاء غير مؤكدة تُفحص قبل تكرارها. يتغير إعداد المعاينة إلى Supabase مع إبقاء D1 UUID والمحددات و`workers_dev:false` و`preview_urls:false` وطرق/cron فارغة. نشر Worker خاص فقط ضمن تفويض الخطة؛ لا إنتاج أو DNS.
4. **التحقق السحابي المحدود:** رفع/تنزيل ملف اصطناعي صغير والحجم الأقصى، وتحقق hash والخصوصية ومنع الكتابة العامة، واختبار استعادة معزول. لا ضغط على خدمة الطرف الثالث أو بيانات إنتاج. تعذر حساب/سر/أداة يبقي الخطوة معلقة ولا يحول fixture محليًا إلى دليل تشغيل.
5. **الربط العام في مرحلة5:** Access وTurnstile وBrevo والموقع والإدارة والوسائط العامة واختبار المتصفح وCPU والاستعادة بعناوين صحيحة، ثم مراجعة المالك ونشر إنتاج معتمد. لا يُعتبر توفر bucket أو نجاح build اكتمال لوحة الإدارة الحية.

قبل الإغلاق: مراجعة diff والتغييرات السابقة المحمية، إثبات الاختبارات التي أُجريت، وتحديث سجل الاستئناف بالموارد الحقيقية والحدود المتبقية. لا commit أو push تلقائيًا.

## المراجع المفحوصة

- [API keys](https://supabase.com/docs/guides/getting-started/api-keys): المفتاح الحديث في الخادم، header `apikey`، صلاحياته وحماية الأسرار.
- [Storage buckets](https://supabase.com/docs/guides/storage/buckets/fundamentals) و[إنشاء الحاويات](https://supabase.com/docs/guides/storage/buckets/creating-buckets): الخصوصية وحدود النوع والحجم.
- [Standard uploads](https://supabase.com/docs/guides/storage/uploads/standard-uploads) و[StorageFileApi الرسمي](https://github.com/supabase/storage-js/blob/main/src/packages/StorageFileApi.ts): HTTP للرفع والجسم binary ورفض overwrite والحذف والقوائم المحدودة. اختيار `fetch` يستعمل بروتوكولًا قائمًا دون تثبيت SDK جديد.
- [Serving assets](https://supabase.com/docs/guides/storage/serving/downloads): اختلاف الروابط الخاصة والعامة وخيار PDF `download`.
- [Storage schema](https://supabase.com/docs/guides/storage/schema/design): metadata داخل PostgreSQL والعمليات عبر API.
- [Database backups](https://supabase.com/docs/guides/platform/backups): ملفات Storage تحتاج نسخة مستقلة.
- [Pricing](https://supabase.com/pricing): الحصص والخمول، وليست قياسًا لقدرة التطبيق الفعلية.
