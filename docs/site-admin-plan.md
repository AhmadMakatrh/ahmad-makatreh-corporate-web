# خطة لوحة إدارة الموقع

**الحالة:** تم تنفيذ إدارة الطلبات والأسعار والعروض والمحتوى والصفحات داخل `client/src/admin/` محليًا. تفعيل Access وربط نطاق الإدارة وترحيلات قاعدة الإنتاج ما زالت مطلوبة. [الاستخدام وميزانية الاستعلامات](admin-dashboard.md).

## الهدف

إنشاء لوحة إدارة خاصة على `admin.ahmad-makatreh.vip` لإدارة محتوى الموقع بالعربية والإنجليزية، والباقات والأسعار والعروض، والصفحات الجديدة، وطلبات التواصل. بعد تجهيز آلية المحتوى، يمكن تعديل المحتوى المنشور من اللوحة من دون إعادة بناء ملفات الواجهة لكل تعديل.

## ما هو موجود حالياً

- واجهة React/Vite ثابتة، ويحدد إعداد Wrangler مجلد `dist` كأصول الموقع.
- API مبني على ASP.NET Core وقاعدة PostgreSQL لحفظ طلبات التواصل. يحفظ الخادم الطلب قبل محاولة إرسال إشعار البريد.
- المحتوى موزع بين ملفات اللغة العربية والإنجليزية وملفات بيانات المشاريع والمقالات ومكونات الصفحات.
- مسارات الموقع الحالية معرفة في الواجهة؛ لذلك تحتاج الصفحات الجديدة إلى مسار عام يعتمد على slug ومحتوى الصفحة المنشور.
- أسعار الباقات ونسب الخصم موجودة في صفحة الخدمات، بينما نص النافذة المنبثقة للعرض موجود في ملفات اللغة ومكون مستقل. ينبغي توحيد مصدرهما.
- إشعار البريد معطل في الإعداد الافتراضي. الإعداد الحالي يستخدم SMTP على المنفذ 587 مع STARTTLS، وعنوان الاستقبال الافتراضي `info@ahmad-makatreh.vip` لم يؤكد بعد.
- لا توجد حالياً واجهة إدارة أو مصادقة خاصة بها أو واجهات API لإدارة المحتوى والطلبات.

## النطاق الوظيفي

### إدارة المحتوى والصفحات

- تحرير النصوص والعناوين والوصف والصور والروابط الظاهرة في صفحات الموقع الحالية باللغتين.
- إدارة بيانات الأعمال والمشاريع والمقالات والصور المرتبطة بها.
- إنشاء صفحة من قوالب وأقسام معتمدة على تصميم الموقع، وترتيب الأقسام، وتحديد slug وعنوان الصفحة وبيانات SEO.
- التحكم بظهور الصفحة في قائمة الموقع.
- حفظ مسودة ومعاينة الصفحة قبل النشر، مع سجل نسخ لاستعادة محتوى سابق.
- تخزين المحتوى المنظم بدلاً من السماح بإدخال HTML غير مقيد؛ ذلك يحافظ على ثيم الموقع ويحد من مخاطر إدخال محتوى نشط.

تظل الألوان والخطوط والحركات وسلوك المكونات مسؤولية الواجهة، بينما تكون النصوص والبيانات والصور وترتيب الأقسام قابلة للإدارة. أي تعديل مستقبلي على نظام التصميم نفسه يظل تغييراً برمجياً.

### الباقات والأسعار والعروض

- إنشاء الباقات وتعديلها وترتيبها وإخفاؤها، مع النصوص والميزات باللغتين.
- إنشاء العروض وتعديلها وإيقافها أو إخفاؤها بعد انتهائها، وربط كل عرض بباقة أو أكثر.
- جعل سعر الباقة والعرض ونسبة الخصم المعروضة في صفحة الأسعار والنافذة المنبثقة من مصدر بيانات واحد، مع التحقق من اتساقها قبل النشر.
- الحفاظ على مفاتيح الباقات المستخدمة حالياً في نموذج الطلبات، أو تحديث الربط بين الباقة والطلب بصورة متوافقة عند السماح بمفاتيح جديدة.

### الطلبات والبريد

- قائمة للطلبات مع البحث والتصفية بالتاريخ والفئة والحالة، وصفحة تفاصيل لكل طلب.
- تعديل حالة الطلب ومتابعته من اللوحة.
- عرض نتيجة محاولة إشعار البريد منفصلة عن حالة الطلب. الطلب يبقى محفوظاً حتى عند فشل البريد؛ وحالة `accepted` تعني أن خادم الإرسال قبل الرسالة، ولا تثبت وحدها وصولها إلى صندوق الوارد.
- توثيق نتيجة الإرسال وتوقيتها في قاعدة البيانات إذا كان المطلوب متابعة حالة البريد من اللوحة؛ فهي لا تُحفظ حالياً ضمن كيان الطلب.
- وضع أسرار البريد في إعدادات الخادم السرية، لا في الواجهة أو قاعدة محتوى اللوحة.

## البنية المقترحة

1. تبقى لوحة الإدارة واجهة React منفصلة على `admin.ahmad-makatreh.vip`، وتستخدم API الحالي المبني على ASP.NET Core.
2. تحفظ الصفحات ومكوناتها المنظمة والباقات والعروض والطلبات في PostgreSQL. يقدم الـAPI المحتوى المنشور للزوار، ويقصر عمليات التحرير والنشر على واجهات إدارة محمية.
3. تحفظ الصور في مخزن كائنات منفصل عن ملفات التطبيق؛ يمكن تقييم Cloudflare R2 لأن الموقع يستخدم Cloudflare، مع رفع مؤقت مصرح به والتحقق من النوع والحجم قبل اعتماد الملف. [توثيق رفع R2](https://developers.cloudflare.com/r2/objects/upload-objects/)
4. تحمي سياسة Cloudflare Access نطاق الإدارة بهوية المالك فقط. ويجب أن يتحقق الخادم من رمز Access وتوقيعه وصلاحياته عند الوصول إلى API الإدارة؛ وجود نطاق فرعي منفصل وحده لا يمنع استدعاء API مباشرة. [تطبيق Access مستضاف](https://developers.cloudflare.com/cloudflare-one/access-controls/applications/http-apps/self-hosted-public-app/) · [التحقق من JWT](https://developers.cloudflare.com/cloudflare-one/access-controls/applications/http-apps/authorization-cookie/validating-json/)
5. يظل مسار إرسال نموذج التواصل العام منفصلاً عن صلاحيات لوحة الإدارة، مع إبقاء التحقق من المدخلات والحماية من الإغراق.

## البريد

قبل تفعيل الإرسال، يجب تأكيد عنوان الاستقبال واختيار خدمة الإرسال وتجهيز إعدادات نطاق المرسل وDNS. إذا اختير Cloudflare Email Sending، فتتطلب خدمة SMTP الحالية لديها TLS مباشراً على المنفذ 465، بينما يستخدم التطبيق حالياً STARTTLS على 587؛ يلزم عندئذ تغيير إعداد الاتصال في الخادم وتخزين رمز Cloudflare كسر. [توثيق SMTP في Cloudflare Email Service](https://developers.cloudflare.com/email-service/api/send-emails/smtp/)

## مراحل التنفيذ

1. **أساس الإنتاج والحماية:** التحقق من استضافة API وPostgreSQL، وضبط دخول الإدارة والتحقق الخادمي من الهوية، وحسم البريد.
2. **العمليات:** واجهة الطلبات وحالاتها، ثم إدارة الباقات والعروض وربطها بصفحة الأسعار والنافذة المنبثقة.
3. **المحتوى الحالي:** نقل النصوص والصور والبيانات الموجودة تدريجياً إلى مخطط محتوى يدعم العربية والإنجليزية، مع التحقق من بقاء الصفحات الحالية كما هي بصرياً.
4. **الصفحات الجديدة:** بناء قوالب الأقسام، وترتيبها، وإدارة المسودات والمعاينة والنشر والقائمة وSEO.
5. **التحقق قبل الإطلاق:** اختبار الصلاحيات، والرفع، والنشر بالعربية والإنجليزية، والروابط المباشرة، وسلوك الموقع عند تعذر API أو قاعدة البيانات، واستعادة نسخة محتوى سابقة.

## قرارات ما زالت مفتوحة

- عنوان البريد الذي سيستقبل الطلبات.
- هل خدمة Cloudflare Email Sending مفعلة على الحساب، أم سيستخدم SMTP لمزود آخر.
- تفعيل نطاق الإدارة المعتمد `admin.ahmad-makatreh.vip` وإعداد تطبيق Access ومصدر الدخول وسياسة MFA.
- قرار مخزن الصور النهائي وحجم الرفع المسموح.

## حدود هذه الخطة

هذا الملف يوثق النطاق والاتجاه المعماري فقط. لا ينشئ لوحة الإدارة أو قواعد بياناتها ولا يغير إعدادات DNS أو ينشر أي شيء.
