# لوحة إدارة الموقع

لوحة الإدارة تعمل على `admin.ahmad-makatreh.vip` من خلال Worker مستقل. الواجهة في `frontend/src/admin/`، ومدخل Worker في `deploy/cloudflare/admin-worker.js`، ومعالجات API المشتركة في `backend/cloudflare/src/`. تستخدم D1 لحفظ البيانات، وSupabase Auth لدخول المالك، وSupabase Storage للوسائط، وBrevo لإرسال البريد. يوضح [مرجع المعمارية](current-architecture.md) حدود هذه المكونات ومسار .NET البديل.

## أقسام اللوحة

| القسم | الوظائف المتاحة |
| --- | --- |
| الطلبات | البحث بالاسم والبريد والمرجع، والتصفية بالفئة والحالة ونتيجة إشعار البريد والتاريخ؛ عرض 25 طلبًا في الصفحة؛ تعديل الحالة والملاحظات؛ إرسال رد يدوي وقراءة سجل الردود |
| الأسعار والعروض | تحرير الباقات باللغتين وأسعارها ومزاياها وترتيبها وإظهارها، وضبط العروض ومواعيدها والباقات المشمولة والنافذة الترويجية |
| المحتوى والصور | تحرير نصوص الموقع وصور الهوية، وإدارة الأعمال والمقالات وترتيبها وإظهارها |
| الصفحات | إنشاء صفحات من أقسام قابلة للترتيب، وتحرير المسار والظهور في القائمة وبيانات البحث، ومعاينة اللغتين |
| مكتبة الوسائط | رفع PNG وJPEG وWebP وPDF حتى 10 MiB للملف، واختيار الملفات وأرشفتها؛ عرض 25 ملفًا في الصفحة |
| النسخ الاحتياطي | تنزيل مستندات المحتوى والأسعار والصفحات، واستعادة مستند مختار إلى المسودة؛ استيراد الطلبات المفقودة من ملفات التصدير |

## الحفظ والنشر والاستعادة

1. التحرير داخل النموذج يبقى محليًا إلى أن تضغط **حفظ المسودة**. لا يتغير المحتوى العام بهذا الحفظ.
2. راجع المسودة ثم اضغط **نشر**. الموقع العام يقرأ المستندات المنشورة فقط.
3. سجل النسخ يعرض العملية والوقت والمالك. استعادة نسخة من السجل تنشئ مسودة جديدة تحتاج مراجعة ونشرًا مستقلًا.
4. **استعادة المنشور السابق** تعيد نشر النسخة السابقة مع الاحتفاظ بالمسودة الحالية.
5. كل كتابة للمستند تحمل `expectedRevision`. اختلاف النسخة يرد `409`، فلا يُكتب فوق تعديل جلسة أخرى. تحديث الحالة والملاحظات يستخدم `expectedUpdatedAtUtc` للغرض نفسه.

يحفظ العميل قراءات الإدارة في ذاكرة التبويب لمدة 60 ثانية، بحد أقصى 40 نتيجة، ويشارك الطلبات الجارية إلى المسار نفسه. التحديث اليدوي يتجاوز النسخة المحفوظة، والكتابة تبطل القراءات المتعلقة بها. بيانات الطلبات لا تُحفظ في `localStorage` بواسطة عميل الإدارة.

المحتوى العام له ذاكرة لمدة 30 ثانية داخل كل Worker isolate، مع ETag و`max-age=30`. بعد كل قراءة، يجدول العميل قراءة جديدة بعد 30 ثانية أثناء ظهور التبويب واتصاله بالشبكة، ويعيد التحقق أيضًا عند العودة إلى التبويب أو عودة الاتصال. تشترك البطاقة والأسعار في هذه البيانات، فتنعكس التعديلات المنشورة دون إعادة تحميل الصفحة أو نشر الكود. يعيد الطلب التحقق من ذاكرة المتصفح، لكن النشر لا يبطل ذاكرة جميع نسخ Worker في اللحظة نفسها؛ قد يتأخر الظهور إلى أن تتجدد. لا تتداخل القراءات، وتبقى البيانات الحالية أثناء الجلب أو تعذره دون إعادة شاشة التحميل. تحديث HTML المولّد وبيانات المشاركة وملف sitemap يحتاج بناءً ونشرًا جديدين من نسخة المحتوى المنشورة، كما يوضح [دليل SEO](seo-and-geo.md).

## الدخول والجلسة

- حساب المالك هو المستخدم المحدد بمعرّف `ADMIN_ALLOWED_SUB` في Supabase Auth. تطابق البريد وحده لا يمنح الصلاحية.
- الدخول يبدأ بكلمة المرور ثم رمز بريد من ستة أرقام. توجد صفحة لإضافة تطبيق تحقق TOTP احتياطي، ومسار مستقل لاستعادة كلمة المرور. إذا كان عامل TOTP مسجّلًا، يلزم التحقق منه أثناء الاستعادة؛ جلسة الاستعادة وحدها لا تفتح اللوحة.
- الجلسة مشفّرة داخل `__Host-AdminSession` بخصائص `Secure; HttpOnly; SameSite=Strict; Path=/`، وبحد أقصى ثماني ساعات من تسجيل الدخول. يتحقق الخادم من توقيع Supabase من نوع ES256 ومن المستخدم والأصل وحالة التحقق.
- ملفات واجهة الإدارة تمر عبر التحقق قبل تقديمها، وتُرسل مع `private, no-store`. الموقع العام يرفض `/api/admin/*`.
- الكتابة إلى API الإدارة تتطلب Origin مطابقًا ورمز `X-Admin-CSRF` مطابقًا لملف الحماية الموقّع. إذا أرسل المتصفح `Sec-Fetch-Site` فيجب أن تكون قيمته `same-origin`؛ عند غياب الترويسة تبقى حماية Origin وCSRF مطلوبة. التحقق من Origin وFetch Metadata يشمل طلبات `/auth/*` التي تغير الحالة أيضًا. تسجيل الخروج يستخدم `/auth/logout` وينهي جلسة Supabase وملفات الجلسة المحلية عند نجاحه.
- عند `401` لطلب قراءة، يحاول العميل تجديد الجلسة مرة واحدة ثم يعيد القراءة. طلبات الكتابة لا تُعاد تلقائيًا. عند انتهاء الجلسة أثناء التحرير، تبقى التعديلات في التبويب ويمكن إتمام الدخول في تبويب آخر ثم إعادة التحقق.

## الإعدادات المطلوبة

إعداد النشر هو `deploy/cloudflare/wrangler.admin.jsonc`. ملف `deploy/cloudflare/.dev.vars.example` مرجع للأسماء؛ القيم السرية تحفظ خارج Git وفي أسرار Worker المستهدف.

| الإعداد | الغرض |
| --- | --- |
| `ADMIN_ORIGIN` | أصل HTTPS الكامل للوحة؛ يجب أن يطابق أصل الطلب |
| `SUPABASE_URL`, `SUPABASE_PUBLISHABLE_KEY`, `ADMIN_ALLOWED_SUB` | مشروع Auth ومفتاحه العام ومعرّف المالك |
| `ADMIN_SESSION_KEY` | مفتاح من 32 بايت بترميز base64url لتشفير الجلسة |
| `ADMIN_CSRF_KEY` | سر لا يقل عن 32 بايت UTF-8 لتوقيع حماية الكتابة |
| `DB` | ربط D1 للمستندات والطلبات والتاريخ وبيانات الوسائط |
| `MEDIA_PROVIDER=supabase`, `SUPABASE_STORAGE_BUCKET`, `SUPABASE_SECRET_KEY` | تخزين ملفات الوسائط؛ المفتاح السري يبقى في الخادم |
| `BREVO_API_KEY`, `BREVO_SENDER_EMAIL`, `BREVO_SENDER_NAME` | إرسال الردود من اللوحة؛ المرسل يحتاج إعدادًا صالحًا لدى Brevo |

يربط إعداد Worker محددات طلبات منفصلة: 120 طلب إدارة في الدقيقة لكل هوية، وست عمليات رد وست عمليات رفع في الدقيقة لكل هوية، وخمس محاولات دخول في الدقيقة لكل IP. هذه إعدادات حماية وليست قياسًا لسعة النظام.

التشغيل المحلي موضّح في [دليل Cloudflare API](../backend/cloudflare/README.md). ظهور واجهة `admin.localhost` في Vite لا يجهز جلسة الإنتاج؛ مسار الجلسة يتطلب أصل HTTPS مطابقًا وإعداد Auth صالحًا.

### تجهيز Supabase Auth لبيئة جديدة

1. أنشئ مستخدم المالك داخل Supabase Auth، وأوقف التسجيل العام. حساب إدارة مشروع Supabase نفسه ليس حساب دخول الموقع. احفظ UUID المستخدم في `ADMIN_ALLOWED_SUB`.
2. اضبط توقيع JWT على ES256، وهو النوع الذي يقبله الخادم، ومدة JWT على 900 ثانية وفق إعداد التشغيل المعتمد. حد جلسة اللوحة في الكود ثماني ساعات ولا يتغير بهذا الإعداد.
3. جهّز إرسال بريد Auth من إعدادات SMTP في Supabase باستخدام مرسل Brevo صالح. إعداد `BREVO_API_KEY` على Worker يخدم إشعارات الطلبات والردود، ولا يجهز بريد Supabase Auth تلقائيًا.
4. اجعل قالب Magic Link يعرض `{{ .Token }}` لرمز الدخول، وقالب Reset password يعرض الرمز نفسه بدل رابط الاستعادة. تدخل الرموز من ستة أرقام في واجهتي الدخول و`/recover`.
5. اضبط أصل الإدارة والمفاتيح المذكورة أعلاه على Worker الإدارة المقصود. احفظ قيم الأسرار خارج Git، واستخدم حسابًا منفصلًا عند التحقق في بيئة المعاينة.

عند تسجيل عامل TOTP، يبقى مطلوبًا أثناء استعادة كلمة المرور؛ فقدانه يحتاج تدخل المالك من إعدادات مشروع Supabase. لا تمنح جلسة استعادة كلمة المرور وحدها صلاحية فتح اللوحة.

## الطلبات والبريد والوسائط

تعرض واجهة تأكيد الإرسال العامة رسالة استلام ودودة وزر رسالة جديدة فقط، في التواصل وطلبات الخدمات بالعربية والإنجليزية. يبقى الرقم المرجعي وحالة إشعار البريد للمتابعة في لوحة الإدارة، ولا يظهران في تأكيد الإرسال للمستخدم. لا يغيّر ذلك استجابة API أو حفظ بيانات الطلب.

الطلب المحفوظ مستقل عن نتيجة إشعار البريد. `accepted` يعني قبول Brevo للرسالة، ولا يثبت وصولها إلى صندوق الوارد. عند تعطّل إشعارات البريد يبقى الطلب في D1. الرد من اللوحة عملية صريحة لها معرّف يمنع إرسال العملية نفسها مرتين؛ نتائج `pending` أو `unknown` تستلزم مراجعة السجل قبل بدء رسالة جديدة.

تظهر نتائج إشعار الطلب غير المقبولة أو غير المسجلة بشارة تحذير في القائمة والتفاصيل. عند تهيئة `BREVO_API_KEY` و`BREVO_SENDER_EMAIL` و`BREVO_RECIPIENT_EMAIL` على عامل الإدارة، يتيح زر «إعادة إرسال إشعار الطلب» إرسال الإشعار إلى بريد الإدارة للحالات `disabled` و`failed` فقط. يستخدم المسار `POST /api/admin/inquiries/{id}/notification` وقت المحاولة السابق كشرط تحديث ذري؛ تُحفظ حالة `unknown` قبل الاتصال بالبريد لمنع الإرسال المتكرر عند النقر المزدوج أو انقطاع الاتصال. يبقى الطلب محفوظًا، ولا يعاد الإرسال تلقائيًا. نتائج `unknown` و`timedOut` أو غياب الحالة تتطلب مراجعة سجل المزود قبل أي إعادة إرسال. يحدد الخادم أهلية الإعادة عبر `notificationRetryable` مستقلًا عن جاهزية إعدادات البريد. في خادم SMTP البديل تُتاح الإعادة للحالة `disabled` فقط؛ سجلات `failed` القديمة قد تشمل فقدان تأكيد القبول، فتحتاج مراجعة ولا تُعاد مباشرة. تُسجل استثناءات الإرسال الجديدة هناك كحالة `unknown`. لا تُضاف أعمدة إلى قاعدة البيانات أو يُغيّر مخططها.

تصدير الطلبات يخص الصفحة الحالية بصيغة JSON أو CSV. الاستيراد يقبل JSON بصيغة التصدير حتى 100 طلب، ويضيف السجلات المفقودة دون استبدال الموجودة أو إرسال البريد.

رفع الوسائط يحفظ الملف أولًا ثم بياناته في D1. الرابط الناتج من موفر Supabase هو رابط قراءة عام؛ يجب أن تتوافق صلاحيات الحاوية مع نشر صور الموقع. أرشفة الملف ترفض إذا ظل مستخدمًا في مسودة أو منشور، وتُبقي الكائن الأصلي لحماية روابط التاريخ. مكتبة الوسائط مخصصة لأصول الموقع المنشورة وليست مخزنًا لمرفقات المستخدمين الخاصة.

## النسخ الاحتياطي والتحقق

نسخة المستندات من اللوحة لا تشمل تاريخ D1 الكامل أو ملفات Supabase أو حسابات Auth وأسرارها. النسخة التشغيلية الكاملة تحتاج نسخة D1 ونسخة وسائط متوافقتين، مع اختبار الاستعادة إلى موارد معزولة. يوفر `backend/cloudflare/scripts/supabaseMediaTools.js` أدوات فحص ونسخ واستعادة الوسائط؛ راجع [دليل API](../backend/cloudflare/README.md) قبل استخدامها.

راجع [دليل التحقق والإصدار](verification-and-release.md) لأوامر الاختبارات والبناء والتمييز بين التشغيل المحلي والمعاينة والإنتاج. بناء الواجهة واختبارات الخدمات المعزولة لا يثبتان صلاحية حسابات Auth أو وصول البريد في البيئة المنشورة.
